## 結論
```yaml:docker-compose.yml
laravel:
    env_file:
      - ./.env
```
docker-compose.ymlで上記のようなenv_fileでの.env参照(Composeの環境変数)をやめるでした。
https://docs.docker.jp/compose/environment-variables.html

## 経緯
Laravelを5年くらい使ってますが、なぜか毎回コンテナを作り直さないと.envが反映されないという
聞いたことがあるような、無いような~~超不便~~環境に悩まされてました。
当然、下記は試していました。[^1]
```
php artisan cache:clear
php artisan config:clear
php artisan route:clear
php artisan view:clear
composer dump-autoload
php artisan clear-compiled
php artisan optimize
php artisan config:cache
php artisan key:generate
rm -f bootstrap/cache/config.php
```

## 暫定対策
唯一envを反映させることができるコマンド
```
docker compose down laravel nginx
docker compose up -d laravel nginx
```
→ビルドではなく、コンテナの再構築だけなので、30秒くらいで反映できるが、頻繁にテストしたい時などその時間すら惜しい状況。。。


## 気づいたきっかけ
一部bladeファイルを使っている箇所があるのですが、そこはなぜかリアルタイムに反映されていました。
そこから全てではない→そこに糸口がありそうと思い、色々調べたところ、下記の構造に行き着きました。

## なぜこうなるのか
1. `env_file`に書いた値は、コンテナ起動時にプロセスの環境変数として注入され、コンテナを作り直すまで固定される
2. Laravelは（configキャッシュが無ければ）.envファイルを毎リクエスト読み込むが、同名の環境変数がすでに存在する場合はそちらを優先し、.envの値で上書きしない（vlucas/phpdotenvの仕様）
3. 結果、.envファイルをいくら書き換えても、コンテナ起動時に固定された環境変数が勝ち続ける

bladeが反映されていたのは、テンプレートファイルそのものが毎リクエスト参照され、変更があれば再コンパイルされるから。
**「毎回ファイルが読み直されるか、起動時に値が固定されるか」** の差で、bladeと.envの挙動が分かれていました。
どれだけ`config:clear`しても直らなかったのは、Laravelのキャッシュの問題ではなく、そもそも.envより手前で値が決まっていたからでした。

## 注意点（env_fileをいつ使うか）
```yaml:docker-compose.yml
laravel:
    env_file:
      - ./.env
```
の便利どころは`docker compose up -d`した時などでLaravelの外で.envを参照したい時です。
そういった使い方をしていると、問題が出てきてしまうので、それ用の環境変数はそれぞれ作成する形に変えるか、上記のまま利用するしかないです。

使い分けの目安はこんな感じです。
- **使う**: compose内で変数を参照したい時や、本番同様に環境変数経由で値を渡す構成をローカルで再現したい時
- **外す**: ローカル開発で.envを頻繁に書き換えるフェーズ。反映の速さを優先し、コンテナ起動に必要な変数だけ別ファイルに切り出す

[^1]: 自分が調べた限りだと、LaravelのDocker環境で.envがリアルタイムに反映しない対策としてComposeの環境変数に言及した記事はなかったです。
