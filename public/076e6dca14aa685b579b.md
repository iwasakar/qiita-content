レビューで「またこの指摘か…」となった経験はありませんか？　同じ指摘の繰り返しは、する側にもされる側にも純粋にコストです。このリストは、繰り返されがちな指摘を**レビュー依頼前のセルフチェック**で仕組み的に潰すためにまとめたものです。

ただし先に強調しておきたいのは、**全項目を毎回チェックする必要はない**ということ。むしろ全部やろうとすると確実に形骸化します。

## 使い方 — 全部チェックしない

判断軸は3つです。

1. **ツールで検出できる項目は人間がチェックしない**
フォーマッタ・linter・静的解析で拾える項目（インデント、未使用use、デバッグログ残り、命名規約、循環的複雑度など）は設定して終わりにする。人間の目は「設計の意図が正しいか」「横展開漏れがないか」など、ツールが判断できない項目に集中させます。
2. **PRの種類で重点を変える**
緊急のバグ修正なら「基本編」と「セキュリティ編」だけ。新規機能の大きめのPRなら「メソッド編」「パフォーマンス編」まで。リファクタリングPRなら「命名規則編」「メソッド編」が主戦場です。
3. **プロジェクトのフェーズで重みを変える**
検証段階で作り捨ての可能性があるコードに「循環的複雑度は減らせません」まで求めるのは過剰です。逆に長期運用に入ったプロダクトでは「セキュリティ編」「パフォーマンス編」の重みを上げる。**何をどの理由で緩めているかをチームで言語化しておく**のがポイントです。

各章の冒頭に「この章の位置づけ」を一言添えています。

## 基本編
この章の大半はツールに委譲できます。フォーマッタとlinterを先に整備して、人間は「動作確認」「横展開」「PJ個別ルール」に集中するのがおすすめです。

- [ ] コードは全て動作確認済みです
- [ ] インデントはずれていないです
- [ ] フォーマッタは利用しています
- [ ] 関係ないソースは変更していないです
- [ ] `console.log`や`Log::debug`は残っていないです
- [ ] 利用されていないuseは削除しています
- [ ] コピペした箇所は見直しました
- [ ] 同様の修正が必要な箇所など横展開の調査はしました
- [ ] PJ個別のルールを確認しています

## 命名規則編
命名は後から直すコストが高い（呼び出し側すべてに波及する）割に、レビューで一番流されやすい領域です。スペルチェックやケース規約はツールに任せ、人間は「名前が実装の意図を表しているか」を見ます。

- [ ] スペルミスはないです
- [ ] 変数名や関数名を省略する際、誰でも元の省略名称が言える状態です
- [ ] ローマ字表記は避けています
- [ ] 変数名はキャメルケースになっています
- [ ] 限定的なスコープ以外でtmp,result などの汎用的な命名をしていないです
- [ ] 関数名はキャメルケースになっています
- [ ] 関数名は作用や動作がわかりやすいです
- [ ] マジックナンバーは使用していないです
- [ ] ファイル名の大文字小文字に誤りはないです

## メソッド編
「減らせません」と言い切れるかを自分に問う章です。循環的複雑度やネストの深さは静的解析で機械的に検出できるので、しきい値だけチームで決めてツールに任せると楽です。

- [ ] ifやforのネストを減らせません
- [ ] 1関数あたりの記述を減らせません
- [ ] 必要な引数だけ渡しています
- [ ] 引数の数は減らせません
- [ ] 関数の引数は型が指定されています
- [ ] 関数の引数の型でobjectやCollectionを指定している際、他に適切な型はありません
- [ ] 関数の引数の型でnullableにしている際、エラーチェックは十分です
- [ ] 早期リターンはできています
- [ ] ループ処理の行数は減らせません
- [ ] 自前のコレクション処理は実装していないです
- [ ] すでに存在する共通処理を自分で実装していないです
- [ ] 循環的複雑度は減らせません

## コメント編
ツールでは判定できない、人間のレビューの本丸です。ここを削れるプロジェクトはありません。

- [ ] コメントはコードの意図を明確に説明しています
- [ ] 複雑なロジックには適切な説明が付けられています
- [ ] コメントには「コードから読み取れない事」を書いています
- [ ] 定数にはコメントが書かれています

## セキュリティ編
項目は1つですが、見逃したときのダメージが最大の章です。secret scanning系のツールで機械チェックを二重化しておくと、人間の見落としを拾えます。

- [ ] センシティブな情報（パスワード、APIキーなど）はハードコードされていないです

## パフォーマンス編
「最適化されています」はレビュー画面のコードだけでは判断できないことが多い章です。N+1のような典型パターンは開発環境で機械的に検知する仕組み（Laravelなら `preventLazyLoading` など）を入れて、チェック自体を不要にするのが理想です。

- [ ] 不必要なループや処理がないです
- [ ] 大量のデータを扱う場合、メモリ使用量は適切です
- [ ] データベースクエリは最適化されています
- [ ] N+1を発生させる実装はないです

## このリストをチームに導入するなら

リストを共有して「今日から全部チェックしてね」は、ほぼ確実に形骸化します。自分が導入するなら次の順番で進めます。

1. **まずツールへの委譲から始める**
リストを配る前に、フォーマッタ・linter・CIで消せる項目を消す。人間がチェックする項目が少ないほど、リストは守られます。
2. **少ない項目から始める**
最初は「実際にレビューで繰り返されている指摘」だけに絞った数項目でスタートし、定着してから章を増やします。
3. **見直しサイクルをセットで決める**
「指摘ゼロが続く項目は削除（卒業）」「新しく繰り返された指摘は追加」のルールを、ふりかえり等の既存の場に乗せます。項目の入れ替えが起きないリストは死んでいるリストです。
4. **AIレビューに渡せるものは渡す**
機械的に判定できる項目はAIレビューやlintに寄せて、人間のレビューは「この設計でよいか」「仕様の前提は正しいか」という、リストに書けない判断に集中させます。

ゴールはこのリストを完璧に守ることではなく、**ツールと習慣に吸収されてリスト自体が短くなっていくこと**です。
