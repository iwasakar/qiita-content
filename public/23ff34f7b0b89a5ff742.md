Laravel BoostとはLaravelの開発者体験を向上させるMCPです。
Laravel10以上で導入可能なので、MCP Clientが使える環境で開発しているLaravel初学者の方は導入すべきだと思います！
また、Agentが勝手に使ってくれるので、開発が爆速になります！！

:::note info
Laravel Boostは、AIにLaravelの"作法"を教え込み、高品質なコード生成を加速。あなたの開発体験を次のレベルへ引き上げます。
:::

## 何が「爆速」になるのか

「爆速」と言いっぱなしでは伝わらないので、**何の往復作業が減るのか**を分解しておきます。

- **バージョン整合の確認が減る**
    - AIは平気で古いLaravelの書き方を提案してきます。Boost導入後はAgentが実際のLaravel・PHP・パッケージのバージョンを確認してから生成するので、「そのメソッド、このバージョンにないんだけど…」と人間が指摘して書き直させる往復が減ります。
- **Eloquentの"作法"を教える手間が減る**
    - モデル定義やDBスキーマをAgent自身が読みに行くので、テーブル構造をプロンプトに貼り付けて説明する作業が要らなくなります。
- **公式ドキュメントとの往復が減る**
    - AgentがLaravel公式ドキュメントを直接検索します。ブラウザでドキュメントを開いてコピペしてAIに渡して…という往復が不要になります。
- **エラー調査の初動が速くなる**
    - Agentがログファイルから最新のエラーを直接読むので、「ログを貼ってAIに聞く」コピペ作業が減ります。

つまり速くなるのは、コードを書く速度そのものというより「**AIにコンテキストを手作業で渡す時間**」です。AIとの往復回数が減るのが体感の正体だと思っています。

## 導入する？見送る？の判断軸

冒頭で「導入すべき」と書きましたが、無条件ではありません。私なりの判断軸はこうです。

| 状況 | 判断 |
| ---- | ---- |
| Laravel 10以上 + MCP Client（GitHub Copilot / Claude Code等）導入済み | **入れる価値大**。composerで1パッケージ追加するだけなので、実質的な導入コストは後述のmcp.json調整くらい |
| AIにスキーマやバージョンを毎回説明するのが面倒になっている | **入れる価値大**。まさにその往復を消すためのツール |
| Laravel 9以下のプロジェクト | **見送り**。Boostより先にアップグレードするかどうかの判断が必要 |
| チームにMCP Clientが未導入 | **見送り（先にそっち）**。Boost単体では何も起きないので、まずエディタ＋AI環境の整備から |
| DBやコード実行をAIに触らせることに合意がないチーム | 入れる前に要相談。後述のDatabase Query / Tinkerは任意のクエリ・コードを実行できるので、**どこまで許可するかを先に握っておく**のが安全 |

## インストール

```sh
composer require laravel/boost --dev
```

```sh
php artisan boost:install
```

これで動くかと思いきや、、、
`boost:install`が生成した下記のmcp.jsonでは、私のDocker環境では動きませんでした。

```json
{
  "servers": {
    "laravel-boost": {
      "command": "php",
      "args": [
        "artisan",
        "boost:mcp"
      ]
    }
  }
}
```

私の環境で動いたのは下記でした。
`app-name`はお使いの`docker-compose.yaml`に記載のものを参照してください。

```json
{
  "servers": {
    "laravel-boost": {
      "type": "stdio",
      "command": "docker",
      "args": [
        "exec",
        "-i",
        "app-name",
        "php",
        "artisan",
        "boost:mcp"
      ]
    }
  }
}

```

### なぜ調整が必要なのか（環境差異を先に疑う）

私は最初「エラーが出た→動く設定を探す」という場当たり対応をしてしまったのですが、後から整理すると、疑うべきポイントは最初から1つでした。**このコマンドはどこで実行されるのか？**です。

- MCPのstdio形式では、MCP Client（VSCode）がmcp.jsonに書かれたコマンドを**ホスト側で**起動し、そのプロセスの標準入出力（stdin/stdout）を通信路としてJSON-RPCのメッセージをやり取りします。
- `boost:install`が生成する`php artisan boost:mcp`は「ホストでphpとLaravelが動く」前提の設定です。
- 一方、Docker環境ではphpもLaravelアプリもコンテナの中にいます。ホスト側で`php artisan`を叩いても、そこに目的のアプリケーションはありません。
- そこで`docker exec -i app-name php artisan boost:mcp`に書き換えて、**コンテナ内のプロセスにホストからstdinを繋ぎっぱなしにする**必要があります。`-i`（stdinを開いたままにするオプション）を忘れると通信路が確立できないので注意です。

教訓は「ローカル実行を前提に作られたツールをコンテナ環境に入れるときは、エラーメッセージと格闘する前に、**コマンドの実行場所と入出力の繋がり方**という環境差異をまず疑う」です。この見方を持っておくと、artisanやnode経由で起動する他のMCPサーバーでも同じ調整がそのまま使えます。

## その他のハマりポイント

- Log Channelsに注意
    - tinker、database-queryはローカル用にログを標準出力（stdout）していると邪魔してしまうようなので、止めましょう。
    - これも原因は上のmcp.json調整と同じ構造です。**stdoutはMCPの通信路そのもの**なので、アプリログをstdoutに流すとJSON-RPCのメッセージにログが混ざって会話が壊れます。「MCPが謎の不調」のときは、まずstdoutを汚していないかを疑うと早いです。
- Search-Docsは日本語には対応していないので、英語で調べてもらう必要があります。
- MCP InspectorでMCPをデバッグすると問題対処にたどりつきやすいです。
    - mcp.jsonを書き換えてはVSCodeごと再起動…を繰り返すより、Inspector単体で「そもそもコマンドが起動して応答を返すか」を確認するほうが切り分けが速いです。
