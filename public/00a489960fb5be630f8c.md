MCP ライフしていますか？
MCP、なんだそれ？ってなっていましたが、色々試して便利を実感しています。
どの言語でも使いやすいMCPを紹介するので、これを機にぜひ試してみてください！
有識者の方は、おすすめの使い方や取り上げていないMCPなどを情報交換できると嬉しいです！

ただ、色々試してわかったのは「MCPは入れるほど良い、というものでもない」ということ。
なので本記事では、各MCPについて「何の課題に効くか」「代替手段と比べて何を優先し、何を捨てたか」という判断軸もセットで書きます。最後に「で、4つ全部入れるべき？」問題にも触れます。

:::note info
MCP(Model Context Protocol)とは
AIアプリを外部システムと接続するためのオープンソース標準規格。
例：ChatGPT や Claude が、データソース（ファイル・DB） や ツール（検索・計算）、ワークフロー（特定プロンプト） にアクセスできる。
イメージ：AI用のUSB-Cポート。どんなAIでも統一的に外部接続や連携が可能な拡張機能。
https://modelcontextprotocol.io/docs/getting-started/intro
:::

## おすすめ1 : chrome-devtools
Chrome公式から出たブラウザ操作系のMCPです。画面操作のデバッグをさせたりができます。
リンク:[npm: chrome-devtools-mcp](https://www.npmjs.com/package/chrome-devtools-mcp)

### なぜこれを選んだか
- **解決したい課題** : AIにフロントを修正させたあと、結局自分でブラウザを開いてポチポチ確認する往復が残っていた
- **比較した代替** : Playwright MCP。テストとして資産化したい再現性の高い操作なら Playwright が上
- **優先したもの / 捨てたもの** : コンテキスト使用量の少なさ・動作の速さ・安定性を優先。E2Eテストとしての再現性・資産化は捨てて、そこは Playwright に任せる前提
- **切り替える条件** : 同じ操作を繰り返し流したくなったら（＝再現性が必要になったら）Playwright へ

### 利用ケース

WebサイトのUIテストを自然言語で指示する。
**指示の例:**
「ログインフォームにテスト用メールアドレスとパスワードを入力し、ログインボタンをクリックして、ダッシュボードが表示されるか確認して」
このような指示でE2Eテストを自動化し、手動での確認作業を削減できます。

### 設定例
```json
"chrome-devtools": {
    "type": "stdio",
    "command": "npx",
    "args": [
        "chrome-devtools-mcp@latest"
    ]
}
```

## おすすめ2 : context7
最新ドキュメントを自動的に参照してくれるMCPです。新しいフレームワークや言語を触るときに重宝します。
最新バージョンに対する回答やバージョンによって差分が大きいコンテキストに対しては、
ハルシネーション(錯覚)を起こしやすいのがLLMの欠点ですが、それを見事に補ってくれます。
DeepWikiにも入れることができ、モダンな環境で開発する方には必須レベルのMCPです。
リンク:[GitHub: upstash/context7](https://github.com/upstash/context7)

### なぜこれを選んだか
- **解決したい課題** : 出たばかりのバージョン（Laravel 12 など）について、LLMが古い知識のまま自信満々に間違える
- **比較した代替** : 都度、公式ドキュメントのURLや該当箇所を自分で貼り付ける。精度は出るが「貼り忘れた瞬間」に古い回答が混ざる
- **優先したもの / 捨てたもの** : 参照の自動化（貼り忘れというヒューマンエラーの排除）を優先。ツール呼び出し分のコンテキスト消費と、APIキー管理の手間は受け入れた
- **優先度が下がる条件** : 枯れたバージョンを固定して長く使うプロジェクトなら、必須ではない

### 利用ケース
リリースされたばかりのライブラリ（例：Laravel 12の新機能）についてAIに質問した際に、AIがWeb上の最新公式ドキュメントを参照して、正確な使い方を回答してくれます。これにより、古い情報や誤った情報に基づいたコーディングを防ぎます。

### 設定例
```json
"upstash/context7": {
    "type": "http",
    "url": "https://mcp.context7.com/mcp",
    "headers": {
        "CONTEXT7_API_KEY": "{context7_api_key}"
    },
    "gallery": "https://api.mcp.github.com/v0/servers/dcec7705-b81b-4e0f-8615-8032604be7ad",
    "version": "1.0.0"
}
```

## おすすめ3 : serena
serenaは既存のソースコードをうまくコンテキストにまとめてくれるMCPです。ソースコードを効率的に検索できるよう、うまくキャッシュをしてくれます。 即効性があるというよりは、徐々に効果を実感できるタイプのMCPです。
リンク:[GitHub: oraios/serena](https://github.com/oraios/serena)

### なぜこれを選んだか
- **解決したい課題** : 大規模・レガシーなコードだと、AIが影響範囲を把握するためにファイルを読み漁り、コンテキストがすぐ溢れる
- **比較した代替** : AI標準の grep・ファイル読み込みに任せる。小規模プロジェクトならこれで十分
- **優先したもの / 捨てたもの** : シンボル単位の検索・キャッシュによるコンテキスト節約を優先。初期セットアップ（uvx環境の用意）の手間と即効性は捨てた（効果は徐々に、なのは前述のとおり）
- **判断軸** : コードの規模と寿命。小さい・短命なプロジェクトに入れても恩恵は薄い

### 利用ケース
大規模なレガシーコードのリファクタリング時にAIに質問する。 
**質問の例** : 「この関数 `getLegacyData()` は、プロジェクト内のどこで使われていますか？」 serenaがソースコード全体を解析し、関連するファイルと具体的な使用箇所を一覧で提示してくれます。

### 設定例
```json
"oraios/serena": {
    "type": "stdio",
    "command": "uvx",
    "args": [
        "--from",
        "git+https://github.com/oraios/serena",
        "serena",
        "start-mcp-server",
        "serena==latest",
        "--context",
        "ide-assistant"
    ],
    "gallery": "https://api.mcp.github.com/v0/servers/0658e342-7ae7-493a-b378-a324363ee322",
    "version": "1.0.0"
}
```

## おすすめ4 : microsoft/markitdown
こちらはマイクロソフト公式のMCPで、エクセルやパワポをマークダウン化してくれるMCPです。
設計書をいちいちマークダウンにする際、変換処理が大変だったりしますが、うまいことエクセルをマークダウンの表形式にできます。
こちらの設計書をもとにコーディングやレビューをさせることも可能で、今までとさほど変わらないやり方で要件に沿った実装を可能にします。
他にもPDFや画像なども対応していますが、エクセル上の画像などには対応していないです。
リンク: [GitHub: microsoft/markitdown](https://github.com/microsoft/markitdown)

### なぜこれを選んだか
- **解決したい課題** : 設計書がエクセルで届く環境のまま、AIに仕様を読ませたい。手作業でのMarkdown変換は大変
- **比較した代替** : 手でMarkdown化する／スクショで渡す。前者は時間がかかり、後者は表の構造が崩れがち
- **優先したもの / 捨てたもの** : 「チームの設計書文化（エクセル）を変えない」ことを優先。エクセル上の画像が拾えない制約は受け入れて、画像が情報の本体になっている資料には使わない
- **判断軸** : 設計書がエクセル・パワポ中心のチームかどうか。最初からMarkdown文化のチームなら不要

### 利用ケース
PMから受け取ったExcel形式のAPI仕様書をAIに読み込ませて依頼する。 
**プロンプトの例**: 「この仕様に基づいたLaravelのコントローラーとルートの雛形を作成して」 
markitdownがExcelをAIが解釈可能なMarkdownに変換し、AIがそれを元にコーディングを開始するため、仕様書からのコード生成が非常にスムーズになります。

### 設定例
```json
"microsoft/markitdown": {
    "type": "stdio",
    "command": "uvx",
    "args": [
        "markitdown-mcp==0.0.1a4"
    ],
    "gallery": "https://api.mcp.github.com/v0/servers/976a2f68-e16c-4e2b-9709-7133487f8c14",
    "version": "1.0.0"
}
```

## で、4つ全部入れるべきか？
結論、最初から全部入れる必要はないです。むしろ「便利そうだからとりあえず全部入れる」はアンチパターンだと思っています。

:::note warn
MCPはタダではない
- MCPを登録すると、そのツール定義が毎回コンテキストに載ります。**使っていないMCPもコンテキストを消費し続けます**
- ツールが増えるほど、AIがツール選択を間違える余地も増えます
- 設定のメンテナンスコスト（バージョン追従・APIキーの管理・環境との接続確認）も地味に積み上がります
:::

おすすめは、**いまの自分のボトルネックに刺さるものを1つ入れて、効果を実感してから次**、という順番です。

| プロジェクトの状況 | 最初に入れるなら | 理由 |
|---|---|---|
| 既存の大規模・レガシーコードを触ることが多い | serena | 影響範囲調査でのコンテキスト節約が一番効く |
| フロントの画面デバッグ・動作確認が多い | chrome-devtools | 手動確認の往復が一番のボトルネックになりやすい |
| 出たばかりのフレームワーク・バージョンを使う | context7 | ハルシネーション対策は早いほど傷が浅い |
| 設計書がエクセル・パワポ中心 | markitdown | 既存の文書文化を変えずにAIに乗せられる |

筆者の環境は「出たばかりのLaravel 12 + レガシーなAngularJS + エクセルの設計書」という状況だったので、結果的に4つとも刺さってこの4選になりました。逆に言えば、状況が違えば選ぶべきMCPも違うはずです。

## おわりに
MCPは「便利そうだから入れる」より「この課題に効くから入れる」のほうが、コンテキストも設定メンテも無駄になりません。
まずは1つ、自分のボトルネックに刺さるものから試してみてください！
おすすめの使い方や取り上げていないMCPがあれば、ぜひコメントで情報交換しましょう！
